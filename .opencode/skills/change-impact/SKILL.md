# Влияние diff

Словарь: поверхность, роль, стенд, сборка. Это карта для ручной проверки, не ревью кода.

## Настройки

1. Прочитай `./qa.config.yaml`. Если файла нет, прочитай `~/.config/opencode/qa.config.yaml`.
2. Если обоих нет, остановись и перечисли ключи из `qa.config.example.yaml` (в этом репозитории он лежит в `.opencode/qa.config.example.yaml`).
3. Возьми `active`. Если `projects.<active>` нет, остановись.
4. Обязательны непустые `project.root`, `project.base_branch`, `task.branch`. `root: .` — рабочая директория OpenCode.
5. Если `task.stand` или `task.role` заданы, сверь их со списками проекта. Чужой id — остановка.
6. URL стенда не открывай. Не вызывай curl, wget, HTTP-клиенты, скрипты и браузер на стенд. Не делай `git fetch`. Пароли не проси и не записывай.

## Что сделать

1. Проверь, что база и ветка есть локально:

```bash
git -C "<root>" rev-parse --verify "<base_branch>"
git -C "<root>" rev-parse --verify "<task.branch>"
```

Если команды не проходят, остановись и попроси человека дать локальную ветку или вставить diff. Сам ветку не скачивай.

2. Сними изменения ветки относительно базы:

```bash
git -C "<root>" diff --stat "<base_branch>...<task.branch>"
git -C "<root>" log --oneline "<base_branch>..<task.branch>"
git -C "<root>" diff "<base_branch>...<task.branch>"
```

3. Сгруппируй diff по поверхностям, которые видит человек или которые меняют его сценарий: экран, эндпоинт, право, флаг, миграция, фоновая задача. Не перечисляй файлы списком без этой привязки. Крупный diff читай выборочно по таким местам, а не копируй целиком в ответ.
4. Раздели обязательный ретест и соседнюю регрессию.
5. Отметь, что diff не доказывает и остаётся только проверке на стенде человеком.

Не оценивай стиль кода и не ищи уязвимости.
