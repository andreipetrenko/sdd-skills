# Ретест фикса

Словарь: поверхность, стенд, сборка. Прогон на стенде делает человек.

## Настройки

1. Прочитай `./qa.config.yaml`. Если файла нет, прочитай `~/.config/opencode/qa.config.yaml`.
2. Если обоих нет, остановись и перечисли ключи из `qa.config.example.yaml` (в этом репозитории он лежит в `.opencode/qa.config.example.yaml`).
3. Возьми `active`. Если `projects.<active>` нет, остановись.
4. Обязательны непустые `project.root`, `project.base_branch`, `task.bug_id`, `task.fix_branch`. `root: .` — рабочая директория OpenCode.
5. Исходные шаги дефекта бери из `task.notes`. Если там нет воспроизведения этого `bug_id`, остановись и попроси шаги. Не восстанавливай их по догадке и не проверяй стенд.
6. Если `task.stand` или `task.role` заданы, сверь их со списками проекта.
7. URL стенда не открывай. Не вызывай curl, wget, HTTP-клиенты, скрипты и браузер на стенд. Не делай `git fetch`.

## Что сделать

1. Проверь локальные базу и ветку фикса:

```bash
git -C "<root>" rev-parse --verify "<base_branch>"
git -C "<root>" rev-parse --verify "<fix_branch>"
```

Если ветки нет локально, остановись и попроси человека. Сам её не скачивай.

2. Посмотри только фикс:

```bash
git -C "<root>" diff --stat "<base_branch>...<fix_branch>"
git -C "<root>" log --oneline "<base_branch>..<fix_branch>"
git -C "<root>" diff "<base_branch>...<fix_branch>"
```

3. В ответ положи исходный шаг из заметок.
4. Дай 2–5 соседних проверок по поверхностям, которые задевает diff фикса. Не переписывай план всей задачи.
5. Отдельным списком напиши, какой регресс вокруг фикса повторно гонять не нужно.

## Ответ

```markdown
# Ретест <bug_id>

Корень: <root>
База: <base_branch>
Ветка фикса: <fix_branch>
Стенд: <id или «не задан», не открывался>
Сборка: <build или «не задана»>

## Исходный шаг
1. ...
Ожидание после фикса: <из заметок или критерия, иначе «в заметках не задано»>

## Соседние проверки
1. Поверхность: ...
   Действие: ...
   Ожидание: ...

## Повторно не гонять
- ...
```
